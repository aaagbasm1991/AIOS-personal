## 取捨

這些原則偏向謹慎而非速度。單純、風險低的小改動可以用判斷力簡化流程，不必每次都走完整 plan → verify。

## 四項原則

### 1. 先釐清（Think Before Coding）

動手前把假設講清楚；不確定就問，不要藏著困惑硬做。有多種解法時全部列出來，不要悶頭選一個。如果有更簡單的做法，直接說，必要時反駁需求。卡住就停下來，明確講出困惑點再問。

### 2. 保持簡單（Simplicity First）

只寫解決問題所需的最少程式碼，不加沒人要的東西：

- 不做超出需求的功能。
- 不為單次使用的程式碼建立抽象。
- 不加沒人要求的「彈性」或「可設定性」。
- 不處理不可能發生的情境。

自問：「資深工程師會不會覺得這樣太複雜？」會的話就簡化。

### 3. 手術式修改（Surgical Changes）

只碰必須改的地方，只清理自己弄出來的東西：

- 不順手「改善」旁邊的程式碼、註解或格式。
- 不重構沒壞的東西。
- 沿用既有風格，即使不是自己會選的寫法。
- 發現沒關係的死碼，只回報，不要動手刪。
- 因為自己的修改而變成沒用的 import／變數／函式要清掉；但不要清理修改前就存在的死碼（除非另外被要求）。

檢驗標準：每一行改動都應該能直接對應到使用者的需求。

### 4. 目標驅動驗證（Goal-Driven Execution）

把任務轉成可驗證的成功標準，照 plan → verify 迴圈執行：

- 「加驗證」→「針對不合法輸入寫測試，再讓測試通過」
- 「修 bug」→「先寫一個能重現問題的測試，再讓它通過」
- 「重構 X」→「重構前後測試都要通過」

成功標準夠明確，才能自己迴圈驗證到過關；標準太模糊（例如「讓它動起來」）只會需要不斷回頭確認。

## 三步 plan → verify 範例

格式：

```
1. [步驟] → verify: [檢查方式]
2. [步驟] → verify: [檢查方式]
3. [步驟] → verify: [檢查方式]
```

實例——「修正登入表單的 email 驗證 bug」：

```
1. 寫一個重現 bug 的測試（合法 email 被判定失敗）→ verify: 測試目前是紅的
2. 修正 email 驗證邏輯，只動驗證函式本身 → verify: 該測試轉綠，其餘既有測試不受影響
3. 確認沒有引入無關改動 → verify: git diff 只包含驗證函式與新測試
```

## 修改範圍檢查表

送出改動前自問：

- [ ] 每個改動的檔案都跟需求有直接關係？
- [ ] 有沒有「順手」改到沒被要求的程式碼、註解或格式？
- [ ] 新增的抽象／參數／設定是不是這次任務真的需要？
- [ ] 錯誤處理是否只覆蓋真的可能發生的情境？
- [ ] 清掉的 import／變數是不是自己這次改動造成的，而不是原本就存在？
- [ ] 有沒有明確的驗證方式（測試、指令、可觀察結果）證明改動成功？
