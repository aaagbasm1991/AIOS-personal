# Brainstorm 規劃模式

在開始實作前，使用這個 skill 將模糊的想法轉化為具體選項、決策與下一步行動。

目標很簡單：放慢到剛好足以避免做錯方向；一旦輪廓清楚，就果斷推進。

## 硬性門檻

在 brainstorming 期間，除非使用者明確要求繼續，否則不要撰寫程式碼、修補檔案、建立專案骨架，或執行不可逆的實作工作。

brainstorming 期間允許：

- 閱讀相關脈絡並摘要重點。
- 提出簡潔問題。
- 比較不同選項。
- 草擬計畫、規格、綱要、驗收標準與決策表。
- 在訊號足夠時推薦一條路徑。

## 核心行為

先給答案，再做解釋。

採用務實的產品規劃姿態：

- 找出真正目標。
- 區分事實、假設與未知事項。
- 當路徑不清楚時，提供 2-3 個可行方向。
- 推薦其中一個方向，並說明原因。
- 讓輸出易於複製到規格、會議紀錄、Notion 頁面、試算表或任務追蹤工具中。

需要釐清時，一次只問一個問題。如果請求已經清楚，就提出簡短計畫並繼續。

## 階段 1：分類請求

判斷這是哪一類規劃問題：

- 產品或功能想法：釐清使用者、目標、使用情境、限制與成功指標。
- Bug 或技術變更：釐清重現方式、預期行為、風險、責任歸屬與驗證方式。
- 規格或文件：釐清受眾、結構、格式、來源材料與開放問題。
- 遊戲設計或 live-ops 規劃：釐清玩家體驗、規則、經濟、UI、邊界情況、獎勵與失敗狀態。
- 寫作或溝通：釐清受眾、語氣、需要做出的決策與期望行動。

如果任務類型混合，先指出主要類型，其餘作為輔助脈絡處理。

## 階段 2：收集脈絡

在詢問使用者之前，先尋找本地專案中可能已存在的脈絡資訊。

可用來源包含：

- `AGENTS.md`、`README.md`、專案文件與任務筆記。
- 既有規格、模板、寫作樣本或參考檔案。
- 任務涉及程式碼時，檢查目前 repo 結構與近期變更。
- 使用者提供的截圖、檔案、連結或筆記。

只摘要會影響決策的脈絡。

## 階段 3：釐清問題

當資訊不足時，提出能降低最大不確定性的簡潔問題。

好的問題包括：

- 這件事應該產生什麼結果？
- 目標使用者或讀者是誰？
- 哪些限制是固定的？
- 哪個取捨最重要：速度、品質、風險、成本，還是彈性？
- 什麼樣的結果會讓這件事感覺成功？

避免長篇問卷。優先提出一個有力問題；當使用者需要協助選擇時，提供一組簡短選項。

## 階段 4：產生選項

當存在多條路徑時，呈現 2-3 個選項。

使用這個結構：

```markdown
## 選項

| 選項 | 最適合 | 取捨 | 建議 |
| :-- | :-- | :-- | :-- |
| A | ... | ... | ... |
| B | ... | ... | ... |
| C | ... | ... | ... |
```

接著用白話推薦其中一個選項。

## 階段 5：產出計畫

一旦方向清楚，就產出務實計畫。

針對功能或程式工作：

- 目標
- 範圍
- 可能涉及的檔案或模組
- 實作步驟
- 驗證步驟
- 風險與開放問題

針對產品、PM、遊戲設計或文件工作：

- 摘要
- 關鍵決策
- 建議結構
- 使用者面向的行為或內容
- 邊界情況
- 開放問題
- 下一步行動

## 階段 6：必要時儲存草稿

如果輸出是較完整的草稿，且使用者要求儲存成品，請在合適的 workspace 資料夾中建議或建立 Markdown 草稿。

使用日期式檔名：

```text
YYYY-MM-DD_short-topic.md
```

常見位置：

- 一般草稿：`100_Todo/drafts/`
- 規格：`100_Todo/drafts/specs/`
- UI 字串或在地化：`100_Todo/drafts/ui-strings/`
- 專案計畫：`100_Todo/projects/` 或 `100_Todo/projects/igaming/`

## 階段 7：最終檢查

完成前，檢查：

- 是否已區分事實、假設與開放問題？
- 是否有清楚推薦路徑？
- 下一步行動是否具體？
- 使用者是否能將結果複製到工作文件中？
- 除非使用者要求，是否已避免進行實作？

## 輸出風格

- 當使用者使用中文時，預設使用繁體中文，除非他們要求其他語言。
- 先給答案或建議。
- 解釋保持簡潔且務實。
- 比較時優先使用表格；計畫則使用結構化清單。
- 針對規格、UI 字串、在地化與 PM/遊戲設計工作，讓結果易於貼到 Notion、Excel 或正式文件中。
